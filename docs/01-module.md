A gamepad interface in the spirit of WoW ConsolePort for the SWG client
(stage.119798): flyout clusters on the stock toolbar, a UI cursor for ANY desktop
window, a radial menu and popups on the stick. Shipped as a source module,
`hook/consoleport/`, to be built inside the QoL DLL; no loader of its own is
needed.

## What the module does and does not do

It does:
- read the joystick buffer after the normal `GetDeviceData` and track the pad
  state; append synthetic buttons to that same buffer - the D-pad out of the POV
  (JOYB 26..29) and, for the Steam profile, the triggers out of the axes
  (JOYB 30/31);
- move and paint the 24 cells of the toolbar volume
  `/GroundHUD.Toolbar.volume` (`SetLocation`/`SetSize`/`SetProperty`), and add
  decor (button glyphs, modifier glyphs, binding labels) as clones of widgets that
  already exist;
- with a desktop window open, put the pad into UI mode: the events never reach the
  game's input map, the D-pad walks the window's nodes, and the buttons turn into
  synthetic input the client already accepts:
  `UIManager::ProcessMessage` (mouse and keys), `CuiIoWin::warpCursor`,
  `CuiActionManager::performAction` ("inventoryClose", "examine");
- take the binding labels out of the active `InputMap` through
  `CuiInputNames::getInputValueString` - the same thing the toolbar itself does.

It does not: automate actions, change timings, build queues, touch network
traffic, reveal hidden state, or patch the client's code - it only calls the
client's functions by address.

## The integration point (what is needed from QoL)

```cpp
#include "consoleport/core/runtime.h"

// after the UI is loaded (the first frame in the world is enough)
cp::Config cfg;                     // [consoleport] in infinity_qol.ini
cfg.profile = "ds4";                // ds4 | steam
cp::install(cfg);                   // false + cp::status().error if the ABI did not match - the module stays silent

// the runGameLoopOnce hook (0x004237C0), which QoL already has
cp::onFrame();

// hook_DI_GetDeviceData, which QoL already has: after the real call, for the joystick
cp::onDeviceData(dev, rgdod, *pdwInOut, capacityBeforeCall, (dwFlags & DIGDD_PEEK) != 0);
// device loss (Unacquire/DIERR_INPUTLOST)
cp::onDeviceLost(dev);
// the keyboard (Steam Input sends the D-pad and triggers as keys): true = swallow it
if (cp::onKey(scancode, down)) { /* do not pass it to the client */ }

cp::uninstall();                    // on unload
```

The module adds no new hooks. Every binary address is in `abi/addresses.h`
(generated by `tools/abitable.py` from the exe, with the md5 in the header) along
with the signature of each function's first 8 bytes; `cp::install` checks those
and the `UIMessage::*` key statics, and on a mismatch it refuses to work.

## The ABI surface

Functions (address, convention, the evidence - `docs/abi-report.md`):
`UIManager::gUIManager`, `ProcessMessage`, `GetObjectFromPath`,
`GetFocusedLeafWidget`, `PushContextWidget`, `PopContextWidgets`, `AbortDrag`,
`UIBaseObject::GetObjectFromPath`, `UIWidget::SetLocation`,
`UIText::SetLocalText`, `SetPreLocalized`, `UIMessage::UIMessage`,
`CuiIoWin::warpCursor`, `CuiActionManager::performAction`, `addAction`,
`Game::getGameInputMap`, `CuiInputNames::getInputValueString`,
`UIVolumePage::Pack` (the target of the module's only hook), and the STLport
allocator (`allocate`/`deallocate`) for the strings handed to the client as an out
parameter.

The `UIBaseObject`/`UIWidget`/`UIPage` virtuals go by vtable slot (IsA,
GetTypeName, SetProperty, GetProperty, AddChild, RemoveChild, GetChild,
MoveChild, Link, DuplicateObject, SetSize, GetWidgetFromPoint, CanSelect,
SetVisible, Pack). Field offsets: parent, name, location, size, scrollLocation,
flags, the UIPage children list, `SwgCuiToolbar::m_volumePage`. The property names
are the binary's ready-made `UILowerString` globals (`abi/props.h`, 1595 of them).

## Structure

```
hook/consoleport/
  abi/        addresses.h, props.h, abi.json (generated)
  gen/        profiles.h (generated from tools/layout.py: pad profiles, slots, colors)
  core/       types, binary (calls by address), node (the UI tree), ui (gestures), tick, runtime
  input/      pad: the state, D-pad and trigger synthesis, UI mode, the key duplicates
  crossbar/   geometry (ConsolePort flyouts), crossbar (cells, decor, reactivity, badges)
  cursor/     nodes (collecting nodes), navigate (cone/half-plane/wrap), cursor, hints, stack
  windows/    desktop (any desktop window), inventory (a window profile), popup (UIPopupMenu/UIRadialMenu)
  tests/      a mock of the tree and the input, mock_binary (reads the exe from disk), 68 tests
  build.cmd   MSVC x86: the tests (CP_MOCK_BINARY) or consoleport.lib
```

Building: `hook\consoleport\build.cmd` builds and runs `out\cp_tests.exe` (the ABI
is checked against the Test Center `swgemu.exe`, and the path can be given by
`CP_EXE`); `build.cmd lib` gives `out\consoleport.lib` for linking into QoL.

## Behavior

The flyouts. The pane slots: main button k -> slot k, the L2 variant -> 8+k, R2 ->
16+k (k: up, left, right, down, triangle, square, circle, cross). The geometry
follows ConsolePort's `Const.Cluster.Layout` at the client's scale (main 44,
flyout 32, offsets 9/14). Holding L2/R2 for 0.12 s brings the matching flyout into
the cluster's center at full size while main and the second flyout step aside (the
volume's draw order must not be changed - `discoverToolbarSlot` counts the
children in order, so there are no overlaps by construction). The input map for
this model: `python tools\build.py` -> `client-files\input\`.

The cursor. The nodes: buttons, checkboxes, textboxes, lists, volume cells;
navigation is a 45 degree cone with metric L1, then a half-plane up to 2:1
sideways, then a wrap onto the furthest node behind on the same line; the repeat
on hold is 0.125/0.125 s; the arrow travels to the node exponentially
(UItravelTime 4).

Where the windows live. Most of them are on the desktop:
`CuiWorkspace::addMediator` moves a window's page to be a direct child of
`GroundHUD` (in space `HudSpace`), and the client keeps the focused one FIRST in
the child list (`MoveChild(Top)` when it is raised; the client finds focus itself
by the same "first visible mediator" walk in `CuiWorkspace::updateGlow`). A
minority never reaches the desktop: `GameMenu` lies as a page of the root, the
message box in `MsgBox`, the options and the map inside folder pages
(`Opt.OptMain`, `PlanetMap.planetMap`, `pda.inputbox` - all dotted paths from the
mediator factory).

So the module searches for a window from the ROOT in draw order (the first child
is the topmost): the desktop it takes apart by its direct children, a folder page
it passes through one level down, and everything else it tries as a window. The
root order is meaningful - in `ui_root.ui` the game menu is included BEFORE the
ground hud, that is, above it, and the backdrop at the very end, that is, below
everything. A folder is told from a window by its own caption: the close box lies
right on a window's page (`bg.mmc.close` and a few more markup paths), a folder
has none - it belongs to the window inside it. We do not descend into a window
with its own caption, otherwise the inventory would return its inner panel and the
window profile would not match. The HUD furniture (the toolbar, the chat, the
radar, the targets) and the permanent counters (`expMon`, `waypointMon`,
`dpsMeter`, `QuestHelper` and the rest) never get into the window list: otherwise
the desktop would take the pad for good. A server build's own permanent panel is
muted with the `uiSkip` key in `consoleport.ini` (comma separated names) - the
name shows up in the desktop trace.

The shared layout of any window: the D-pad walks the widgets; cross presses (on a
volume cell a double click = `performDefaultAction`); square is a
`ContextRequest`; triangle picks up and puts down; circle cancels a move,
otherwise presses the window's close box (`bg.mmc.close` and a dozen more markup
paths, then a search for a close/cancel button by name), and if there is none,
Escape; L1/R1 are the tabs, and without tabs, scrolling; L2/R2 scroll with the
wheel; R3 is `examine`.

Lists (the journal, mail, the datapad, the options) have no row widgets: `UIList`
draws the rows itself and leads them with the arrow keys over the FOCUSED list. So
a list has a mode: cross enters it (we set the `Focus` property, as the markup
does - `UIWidget::SetProperty "Focus"` calls `SetFocus`), after which the D-pad up
and down leads the rows, cross picks a row with the same Enter the client answers
a double click with, L2/R2 page through, circle goes back out to the widgets, and
left/right lead out by themselves. That the mode is on is visible from the hint
bar.

An individual window's profile (`windows/inventory.cpp`) is an ordinary
`cursor::Window` whose `page()` matched the desktop's current window; it is asked
for the node collection rules, the hints and the buttons, and the generic one
stays the fallback.

The inventory (`GroundHUD.Inventory`): cross is a double click on an item
(performDefaultAction) or a click on a button; square is a ContextRequest (the
radial); triangle picks up and puts down (the normal drag: Down, a move, Move,
Up); circle cancels a move or does `inventoryClose`; L1 is `info.up`; R1 is
`buttonView`; R3 is `examine`. The popup: up/down and cross; the radial: the right
stick picks a sector (Radial.lua: 0 at the top, clockwise, dead zone 0.5), and
cross sends Character '1'+sector - `UIRadialMenu` presses the button itself;
circle is Escape.

## Verification in game

The rig per `README.md` (Test Center, the launcher, the virtual pad). The expected
steps: the toolbar rebuilt into two diamonds; holding L2/R2 gives a flyout; the
binding labels match Options > Controls; open the inventory - the arrow is on the
first item, the D-pad walks the grid, cross/square/triangle/circle behave as
described; the popup and the radial on the stick. The logs: `cp::status()`
(installed, abiOk, crossbarAttached, cursorActive, error).

The desktop was verified in game on 9 Sep 2026 (together with the radial, the
crosshair, the NPC layer and native HID input). What to look at on a regression:
open the journal, the datapad, mail, the options, the map and an examine window in
turn - the trace shows the line `desktop: window NAME`, the D-pad walks the
buttons, circle closes the window; open two windows and click the lower one -
focus must move to it. The line `desktop: ... NAME:furniture/small/empty/WINDOW`
is printed when the cursor attaches and about every 10 s while there is no window:
it shows what the desktop counts as a window and what as furniture (`DESKTOP` is
the desktop itself, `WINDOW` means it has a caption of its own, `folder?` means
there are nodes but no caption: either a folder or a dialog). If the pad goes into
UI mode over nothing, the culprit's name comes from there and is muted with
`uiSkip`.

## Facts about the binary, measured in game on 6 Sep

- `UIVolumePage::Pack` (0x0113C6C0) does NOT check `DoNotPackChildren` (bit 2 in
  +0x120 is looked at only by `UIPage::Pack` 0x010FE200): the toolbar volume
  always lays its children out on a grid by CellSize/CellPadding. The module holds
  the geometry with a per-tick guard after every Pack; `attach()` sets the flag
  just in case, but it must not be relied on.
- Binding labels through `CuiInputNames::getInputValueString` give strings like
  "1, F13, 8, CRS, A+CIR" in game - the module gets them with that same call.
- M3 (L2+R2) through `/ui action toolbarPaneNext`/`Prev` on the press/release of
  the second trigger works: the InputMap sends the release to whichever command
  was on the press.
